## 1. Матрица тулчейнов

Все сборки — `./configure --cc-opt="-O2"` (без `--debug`, т.к. debug-logging
добавляет ветвления в горячие пути и меняет кодогенерацию не по делу), затем
`make -j2 unitd`. Копии дерева исходников — по одной на тулчейн, чтобы
DWARF/пути компиляции не путались между сборками.

| Тулчейн | Команда сборки | Результат | Время `make -j2 unitd` | Размер `unitd` (с debug info) | Размер после `strip` |
|---|---|---|---|---|---|
| gcc 13.3 + glibc | `CC=gcc ./configure --cc-opt="-O2"` | OK | ~9 c | 3 308 080 байт | 542 952 байт |
| clang 18.1.3 + glibc | `CC=clang ./configure --cc-opt="-O2"` | OK | ~9 c | 2 939 168 байт | 519 368 байт |
| musl-gcc (Alpine-подобный) | `apt-get install -y musl-tools`; `CC=musl-gcc ./configure --cc-opt="-O2" --no-regex` | OK, но нужен `--no-regex` | ~8 c | 3 195 728 байт | 522 016 байт |
| clang + musl (target x86_64-linux-musl) | обёртка `musl-clang` (см. §6) + `--no-regex` | OK | ~8 c | 2 913 512 байт | 574 136 байт |

Что «сломалось» и как обошли:
- **musl-gcc**: `./configure` падает на `no PCRE library found` — в контейнере
  установлены только glibc-варианты `libpcre2-dev`, под musl их нет.
  Регэкспы в hot-path список функций не входят (`nxt_http_parse_field_value`
  их не использует), поэтому решение — `--no-regex`, отключающее маршрутные
  regex-фичи целиком. Для полноценного musl CI-лега в реальности нужно либо
  собрать `pcre2` под musl отдельно, либо оставить `--no-regex` осознанно.
- **clang + musl**: в apt нет отдельного `clang-musl` таргета, но в системе
  уже есть `musl-tools` (`/usr/include/x86_64-linux-musl`,
  `/usr/lib/x86_64-linux-musl`), и clang умеет кросс-компилировать под
  `--target=x86_64-linux-musl`, если явно передать `-isystem`/`-B`/`-L` на эти
  пути и слинковать статически. Обёрнуто в скрипт `musl-clang` (ниже) и
  подставлено как `CC` в `./configure`. Единственная проблема — под `-Werror`
  clang ругается на «unused command line argument» (`-L` не нужен при `-c`),
  лечится `-Wno-unused-command-line-argument` в обёртке. Docker для Alpine не
  понадобился — прямой кросс-таргет оказался быстрее и рабочим.

Собственно бинарник musl-clang проверен: `ELF ... statically linked`, `unitd
--version` печатает корректную версию и конфигурацию.

## 2. glibc vs musl: раскладка структур

`pahole` использован против `build/sbin/unitd` (для `nxt_port_s` и
`nxt_port_mmap_header_s`, они компилируются в unitd) и против
`build/src/nxt_unit.o` из `make build/lib/libunit.a` (для
`nxt_unit_ctx_impl_s` — эта структура живёт в библиотеке приложения, не в
`unitd`, поэтому нужен объектный файл, а не сам демон).

**Главный вывод: на x86_64 расхождений в размерах и раскладке НЕТ.**

- `pthread_mutex_t`: 40 байт что под glibc (opaque union), что под musl
  (`union { int __i[10]; ... }`) — оба используют "новый" 40-байтный layout,
  оставленный musl намеренно ABI-совместимым с glibc на x86_64.
- `struct nxt_port_s` — 456 байт, 8 cache-line'ов, идентичная раскладка полей
  и одинаковые holes (3 holes, 8 байт) в обеих сборках.
- `nxt_port_queue_t`, `nxt_app_queue_t` (кастомные NNCQ-очереди, без
  pthread-типов внутри) — 655380 и 5767188 байт соответственно, побайтово
  идентичны.
- `struct nxt_port_mmap_header_s` — 200 байт, идентично.
- `struct nxt_unit_ctx_impl_s` — 17024 байта, идентично вплоть до `pahole`
  вывода символ-в-символ (включая holes и forced alignment).

Вывод для отчёта важен сам по себе: типичное предостережение "pthread-типы
отличаются между libc" **не материализуется на этой платформе** для этих
конкретных структур — потому что musl 1.2.x на x86_64 подгоняет размер
`pthread_mutex_t`/`pthread_cond_t` под glibc-совместимый. На других
архитектурах (armhf, riscv) расхождение может быть реальным — стоит
перепроверить `pahole` при добавлении второй архитектуры в CI.
Практическое следствие: musl-нога CI-гейта нужна прежде всего для контроля
регрессий **кодогенерации/инлайнинга** (другая libc → другая специфика
`memcpy`/`memcmp`/атомиков), а не для контроля layout — под layout она
избыточна на x86_64, но не вредна.

## 3. Инструменты — детальное сравнение

### 3.1 objdump vs llvm-objdump

Тест на mca_harness.o (см. §6) — два независимых чистых пересобора одного и
того же кода (`gcc`), затем `objdump -d --no-show-raw-insn` дважды и diff.

- **Детерминизм**: у обоих инструментов вывод **побайтово идентичен** между
  двумя чистыми пересборками, единственное отличие — строка заголовка с
  именем файла (`<path>: file format elf64-x86-64`), которая тривиально
  чистится нормализацией (`grep -v "file format"`).
- **Символ+смещение, relocations**: оба показывают `call <symbol>` /
  `call *0xNN(%reg)` одинаково информативно; `llvm-objdump` иногда чуть
  компактнее оформляет NOP-паддинг (`data16 data16 data16 data16 cs nopw`),
  но не критично.
- **Скорость** на полном `unitd` (3.3 МБ, debug info): `objdump` — 0.073 c,
  `llvm-objdump-18` — 0.145 c. Оба тривиально быстры для CI (сотни мс на весь
  бинарник, доли мс на 15 функций).
- **`-S`/`--line-numbers`**: у `objdump -dl -S` интерливинг с исходником
  работает через все уровни инлайна (показывает и `mca_nncq_dequeue()`, и
  `nxt_nncq_dequeue()`, и `nxt_nncq_cycle()` как отдельные "функции" со своими
  номерами строк) — очень полезно для разработчика, но **абсолютные пути
  исходников** (`/tmp/.../src/nxt_nncq.h:140`) попадают в вывод — источник
  шума при сравнении между разными checkout'ами/машинами, надо нормализовывать
  (срезать префикс до `src/`).
- **Важная находка про диффы целого бинарника**: при diff'е символа внутри
  реального `unitd` (`nxt_port_read_msg_process`) между baseline и
  regression-3 (реордер структуры) в дифф попали **посторонние** изменения
  адресов вызовов (`call 201f0 <nxt_work_queue_add>` →
  `call 201c0 <nxt_work_queue_add>`) — сами функции не менялись, просто текст
  сдвинулся из-за роста другого объектника. `objdump` печатает целевой символ
  по имени, но обёрнутый в изменившийся числовой адрес — нормализатор должен
  срезать именно ведущий hex-адрес операнда, оставляя только `<symbol>`,
  иначе гейт будет ложно шуметь на каждую сборку, где размер бинарника вообще
  изменился.

### 3.2 llvm-mca

Тест — извлечённое горячее тело `nxt_nncq_dequeue` (retry+CAS цикл, см.
`mca_nncq_dequeue.s`), прогнан `llvm-mca-18 -mcpu=cascadelake --iterations=1000
--timeline --bottleneck-analysis`.

Результат: `Block RThroughput: 3.5`, `IPC: 3.98`, честная per-instruction
таблица портов/latency, `lock cmpxchg` смоделирован (6 uops, latency 8,
throughput 1.0). Работает одинаково хорошо что на gcc-, что на clang-варианте
дизассемблированного цикла (просто разные .s на входе) — инструмент
toolchain-агностичен, ему нужен только текст ассемблера + `-mcpu`. Diff между
двумя версиями .s (регрессия/нет) даёт понятную разницу в таблице портов и
`Block RThroughput` — удобно для developer-side анализа горячих циклов.
Минус: **нужен ручной шаг извлечения ассемблерного тела** цикла из
disassembly в `.s`-файл с метками (автоматизировать несложно — regex по
`objdump -d` между двумя адресами, но готового кода на это нет "из коробки").

### 3.3 OSACA (`pip install osaca`)

Установился за ~10 секунд, `osaca --arch CSX mca_nncq_dequeue.s` — принимает
тот же .s без переделки (плюс — совместимость с llvm-mca-стилем asm). Даёт
port-pressure таблицу и Loop-Carried Dependency анализ (нашёл LCD-цепочку
через `mov (%rdi),%eax` с задержкой 5.0). **Критичный минус для этого
проекта**: `lock cmpxchg` помечен как `X - No throughput/latency information`
— OSACA не в курсе latency/throughput LOCK-префиксных инструкций на
Cascade Lake, и итоговый анализ **не выдаётся** без `--ignore-unknown`.
Поскольку почти все 15 горячих функций — это lock-free/CAS-based
IPC-примитивы (`nxt_nncq_*`, `nxt_port_queue_*`, `nxt_app_queue_*`), это
серьёзное ограничение: OSACA хорошо подходит для чисто арифметических
HPC-циклов, но слабо — для атомик-тяжёлого IPC-кода этого репозитория.

### 3.6 bloaty / nm --size-sort

`bloaty` **недоступен**: отсутствует в apt (`E: Unable to locate package
bloaty`) и не публикуется на PyPI как готовый бинарник
(`ERROR: Could not find a version that satisfies the requirement bloaty`).
Сборка из исходников (bazel/cmake + capstone + protobuf) — не оправдана по
времени ради разовой оценки. Рабочая замена — `nm --print-size --size-sort
-C unitd`, показывает отсортированные по размеру символы с человекочитаемыми
именами; достаточно для диффа "функция X внезапно выросла на N байт" между
двумя сборками — `diff <(nm ... old) <(nm ... new)` по колонке размера.

### 3.7 perf

`perf` (текущей версии под `6.18.44-fc`) отсутствует
(`WARNING: perf not found for kernel 6.18.44-fc`), но найден
version-mismatched `/usr/lib/linux-tools/6.8.0-142-generic/perf` — он
запускается. Аппаратные счётчики (`cycles`, `instructions`) —

скорости горячих циклов делается через `clock_gettime(CLOCK_MONOTONIC)`
микробенчмарком (см. `bench_nncq.c`).

## 4. Корреляция llvm-mca vs измеренная производительность

Микробенчмарк `bench_nncq.c` — 200 млн итераций `dequeue()+enqueue()` подряд
на непустой однопоточной очереди (без реальной contention, но с реальной
последовательной зависимостью по данным между dequeue и следующим enqueue).
Собран отдельно под gcc/clang/musl-gcc с одними и теми же `-O2 -g`.

| Тулчейн | Измеренное время | ns/итерацию (пара dequeue+enqueue) | ≈ циклов/итерацию (×2.8 ГГц) |
|---|---|---|---|
| gcc 13 + glibc | 4.110 c / 2·10^8 | 20.549 нс | ≈57.5 |
| clang 18 + glibc | 4.030 c / 2·10^8 | 20.150 нс | ≈56.4 |
| musl-gcc | 4.118 c / 2·10^8 | 20.591 нс | ≈57.7 |

`llvm-mca -mcpu=cascadelake` на изолированном retry-цикле **только**
`nxt_nncq_dequeue` (без enqueue) предсказал `Block RThroughput = 3.5`
циклов/итерацию для fast-path (без ветвления назад по retry).

**Расхождение примерно в 8× (57 против 3.5–7 циклов) — ожидаемо и объяснимо,
а не ошибка инструмента**: llvm-mca моделирует throughput независимых,
пайплайнящихся итераций (как если бы у нас был массив независимых
`dequeue()`-вызовов на разных очередях), а микробенчмарк — это **строго
последовательная цепочка зависимостей по данным** (значение из `dequeue`
уходит прямо в `enqueue`, оба используют одну и ту же кэш-линию `q->head`
через `lock cmpxchg`), плюс сам бенчмарк гоняет ОБА примитива (dequeue **и**
enqueue) за одну итерацию, а не один dequeue. `lock cmpxchg` на этом железе
реально стоит около 18–20 циклов **латентности** (round-trip к L1/store
buffer с полным ordering), и таких CAS в паре dequeue+enqueue — минимум два
последовательных, что уже даёт ~36–40 циклов латентности плюс ALU-цепочка —
это гораздо ближе к измеренным 57, чем throughput-оценка llvm-mca.
**Практический вывод**: llvm-mca пригоден для сравнения *относительной*
регрессии кодогенерации одного и того же цикла между сборками (что и нужно
CI-гейту — "стало ли хуже расписание портов/число uops"), но **не должен
использоваться как абсолютная оценка задержки** для последовательно
зависимых атомарных операций без явной поправки на латентность `lock`-цепочки.

## 5. Регрессионный тест (3 инъекции)

Все три регрессии внесены в отдельные копии дерева (`reg1-noinline`,
`reg2-volatile`, `reg3-reorder`), пересобраны `unitd` (`make -j2 unitd`,
gcc+glibc), плюс собран `mca_harness.o` там же для чистого символа.
Baseline "шум" проверен параллельно: два независимых чистых пересобора
одного и того же дерева (`h1.o`/`h2.o`) дают **нулевой** diff (только строка
имени файла).

| # | Регрессия | Где | Обнаружена ли objdump/llvm-objdump diff | Обнаружена ли pahole/layout | Ложные срабатывания на чистой пересборке |
|---|---|---|---|---|---|
| 1 | Убрали инлайн, добавили `__attribute__((noinline))` на `nxt_nncq_enqueue` | `src/nxt_nncq.h` | **Да, безошибочно**: ~35 строк инлайненной CAS-логики в `mca_nncq_enqueue` схлопнулись в `endbr64; jmp <nxt_nncq_enqueue>` (внешний вызов вместо инлайна) | н/д (не layout-регрессия) | 0 |
| 2 | `volatile` на горячую локальную переменную `h` в `nxt_nncq_dequeue` | `src/nxt_nncq.h` | **Да, безошибочно**: компилятор перестал держать `h` в регистре, появились `mov %eax,-0x4(%rsp)` / `mov -0x4(%rsp),%eax` (spill/reload на каждой итерации ретрая) | н/д | 0 |
| 3 | Реордер поля `queue` в `struct nxt_port_s` (перенесено из cache-line 6 в cache-line 1) | `src/nxt_port.h` | **Да**: `pahole` показывает сдвиг всех полей после `link` на 8 байт и смену cache-line; в реальном коде `nxt_port_read_msg_process` виден прямой эффект — `call *0xf0(%r12)` → `call *0xf8(%r12)` (сдвиг offset поля `handler`, которое оказалось после `queue`) | **Да, полностью**: другая cache-line, другие holes | 0 (но diff по всему `nxt_port_read_msg_process` содержит 3 *посторонних* изменения адресов вызовов к функциям, чей код не менялся — чистый побочный эффект сдвига размера объектников; нужна нормализация call-таргетов по символу, а не по адресу) |

**Итог по всем трём инструментам disasm-diff (objdump/llvm-objdump) +
pahole: 3/3 регрессии обнаружены чётко, шум на чистой пересборке — 0** (при
условии нормализации имени файла в заголовке objdump и, для случая 3,
нормализации адресов операндов `call`/`jmp` до символьного имени).

## 6. Артефакты эксперимента (в scratchpad, не в tools/perf)

- `mca_harness.c` — TU с `__attribute__((noinline))`-обёртками для всех
  header-only inline горячих функций (`nxt_port_queue_send/recv`,
  `nxt_app_queue_send/recv/cancel`, `nxt_nncq_enqueue/dequeue`,
  `nxt_port_mmap_get_free_chunk`). Компилируется в дереве проекта
  (`-I src -I build/include`) под любой из 4 тулчейнов без единого warning'а
  — рекомендуемый способ дать этим функциям стабильный ELF-символ для
  objdump/llvm-mca без изменения самого продакшен-кода.
- `bench_nncq.c` — автономный микробенчмарк `nxt_nncq_enqueue/dequeue` (со
  стаб-реализацией `nxt_atomic_cmp_set`/`nxt_memzero`, включает только
  `nxt_nncq.h`).
- `mca_nncq_dequeue.s` — вручную извлечённое горячее тело retry-цикла для
  llvm-mca/OSACA.
- `musl-clang` — обёртка для clang+musl кросс-компиляции.
- `disasm_diff.sh` — прототип нормализующего diff'а (для этой оценки; не
  путать с `tools/perf/disasm-diff.sh` от потока OPT).

## 8. Рекомендация

**Основной инструмент CI-гейта: `objdump -d --no-show-raw-insn` (GNU
binutils) + нормализация (срезать заголовок с именем файла и hex-адрес
слева от `<symbol>` в операндах call/jmp) + `nm --print-size --size-sort` как
дополнительный размерный чек.**
Обоснование: детерминизм между чистыми пересборками подтверждён (0 diff,
кроме тривиально чистимой шапки), скорость — миллисекунды на 15 функций,
безошибочно ловит все 3 инжектированные регрессии, не требует установки
(есть в базовом `binutils` на любом раннере, включая Alpine). `llvm-objdump`
— равноценная по качеству альтернатива и допустимый второй источник (для
double-check в спорных PR), но не даёт преимуществ, которые оправдали бы
дополнительную зависимость от `llvm` в CI-образе, если `binutils` уже есть.

**Дополнительно в CI-гейт: `pahole -C <struct>` по списку структур
(`nxt_port_s`, `nxt_port_queue_t`, `nxt_app_queue_t`,
`nxt_port_mmap_header_s`, `nxt_unit_ctx_impl_s`)** — единственный инструмент
из проверенных, который поймал регрессию №3 (реордер полей) на уровне
"что именно изменилось в структуре", а не только "код изменился где-то".
disasm-diff это тоже ловит, но пост-фактум (после того как offset уже
просочился в код) — pahole даёт прямой, читаемый diff по layout.

**Для developer-анализа горячих циклов: `llvm-mca` (`-mcpu=cascadelake`
или актуальная модель CI-раннера, определяемая один раз из
`/proc/cpuinfo` → таблица flags → ближайший известный `-mcpu`),
`--timeline --bottleneck-analysis --instruction-tables`.**
Обоснование: единственный из проверенных инструментов, который полноценно
моделирует `lock cmpxchg` (ключевая инструкция всех 15 горячих функций) и
даёт наглядную timeline/bottleneck картину. OSACA — не рекомендуется как
основной инструмент именно для этого кода, поскольку не моделирует
LOCK-префиксные инструкции на целевой микроархитектуре (`X - No
throughput/latency information`) и требует `--ignore-unknown`, чтобы вообще
выдать анализ; можно оставить как secondary sanity-check для
неатомарных горячих участков (например, парсинг `nxt_http_parse_field_value`).
llvm-mca-числа — это **относительная**, а не абсолютная метрика: использовать
их для сравнения "до/после" одного и того же цикла между сборками, не как
предсказание реальных ns/iter (см. §4, расхождение ×8 с измеренным временем
из-за латентностной, а не throughput-природы однопоточной CAS-цепочки).

**Компиляторные remarks (`-fopt-info-missed`, `-Rpass-missed`) — не в
CI-гейт**, слишком шумны файл-широко (2247 строк на один .c у gcc). Годятся
только как ручной, точечный (`grep <имя_функции>`) инструмент разработчика
при расследовании конкретной регрессии, которую уже нашёл disasm-diff.

**Toolchain(и) для пиннинга базовой линии CI-гейта:**
- Основная (gate-blocking) нога: **один зафиксированный `clang 18 + glibc`
  build** (`CC=clang ./configure --cc-opt="-O2"`, без `--debug`). Clang даёт
  более компактный и предсказуемый output (меньше "мусорных"
  mov-перестановок между эквивалентными регистрами, см. пример
  `mca_nncq_dequeue` в §3.1/§6, где clang сразу переиспользует `%ecx` вместо
  промежуточного `%esi`→`%edx`→`%ecx` у gcc) — меньше шанс ложного шума от
  незначащих перестановок при апгрейде компилятора минорной версии.
- Вторая (non-blocking, layout-only) нога: **`musl-gcc + --no-regex`** —
  запускать `pahole` по тому же списку структур и объектнику `nxt_unit.o`
  из `libunit.a`, **не** гонять полный disasm-diff по musl (см. §2 — на
  x86_64 разницы в layout нет, а разница в кодогенерации `memcpy`/атомиков
  между musl и glibc будет постоянно шуметь как false positive относительно
  clang+glibc базовой линии, если гонять один и тот же порог regressions).
  Цель musl-ноги — поймать, если *ABI-специфика когда-нибудь начнёт
  реально отличаться* (например, при переходе на другую архитектуру), а не
  дублировать x86_64 disasm-гейт.
- `gcc + glibc` держать в матрице сборки (раз она уже используется как
  один из production-тулчейнов), но не как источник baseline для diff —
  как дополнительный "он вообще собирается и не деградировал катастрофически"
  smoke-таргет, без строгого построчного сравнения кода.

## 9. Точные команды для внедрения

```sh
# --- сборка эталонной (gate) ноги: clang + glibc ---
CC=clang ./configure --cc-opt="-O2"
make -j2 unitd

# --- сборка layout-ноги: musl-gcc ---
apt-get install -y musl-tools
CC=musl-gcc ./configure --cc-opt="-O2" --no-regex
make -j2 unitd
# для nxt_unit_ctx_impl_s (в libunit, не в unitd):
make -j2 build/lib/libunit.a

# --- (опционально) clang + musl кросс, если понадобится вторая gate-нога ---
cat > musl-clang <<'EOF'
#!/bin/sh
exec clang --target=x86_64-linux-musl -Wno-unused-command-line-argument \
    -isystem /usr/include/x86_64-linux-musl \
    -B/usr/lib/x86_64-linux-musl -L/usr/lib/x86_64-linux-musl -static "$@"
EOF
chmod +x musl-clang
CC=$PWD/musl-clang ./configure --cc-opt="-O2" --no-regex
make -j2 unitd

# --- disasm-diff по одной горячей функции (нормализация для CI) ---
objdump -d --no-show-raw-insn --disassemble=<symbol> old/build/sbin/unitd \
    | grep -v "file format" \
    | sed -E 's/^[0-9a-f]+ <[^>]+>:/<FUNC>:/' \
    | sed -E 's/^ *[0-9a-f]+:/ADDR:/' \
    | sed -E 's/(call|jmp) +[0-9a-f]+ (<[^>]+>)/\1 \2/' \
    > old.norm.txt
# аналогично для new/, затем:
diff -u old.norm.txt new.norm.txt

# --- layout-гейт: pahole по ключевым структурам ---
pahole -C nxt_port_s             build/sbin/unitd
pahole -C nxt_port_mmap_header_s build/sbin/unitd
pahole -C nxt_unit_ctx_impl_s    build/src/nxt_unit.o

# --- llvm-mca для developer-анализа горячего цикла ---
# 1) извлечь тело цикла в .s вручную (метки loop:/retry:/cas: как ориентиры)
llvm-mca-18 -mcpu=cascadelake --iterations=1000 \
    --timeline --bottleneck-analysis --instruction-tables loop.s

# --- размерный дифф по символам ---
nm --print-size --size-sort -C build/sbin/unitd > sizes.new.txt
diff <(sort -k2 sizes.old.txt) <(sort -k2 sizes.new.txt)

# --- получить standalone-символы для header-only inline функций ---
# добавить тест-таргет TU src/mca_harness.c с __attribute__((noinline))-
# обёртками (см. §6, mca_harness.c) и собирать его тем же CC/CFLAGS, что и
# основной unitd, для стабильного символа под objdump/llvm-mca без
# изменения продакшен-заголовков.
```
