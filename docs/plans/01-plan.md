# FreeUnit: code factory + Drupal Harness. Итоговый план на 5 + 3 дня

Сводный документ. Источники:
- план, который субагент составил по коду;
- анализ git за 6 месяцев (526 коммитов на master), 20 открытых PR и 41 открытой задачи;
- поиск в вебе (Gander и OTel-стек).

Места, помеченные **[гипотеза]**, не проверены до конца. По каждому сначала нужен воспроизводящий тест, потом исправление.

## 0. Выводы, на которых строится план

1. **Фабрика уже работает, но нестабильно.** Как минимум 57% коммитов за полгода сделаны с участием LLM. Тест попадает в тот же коммит только в 53% случаев, когда меняется `src/*.c|h`. Правки к одной теме часто доделываются ещё 1–2 днями: первый проход LLM не покрывает граничные случаи. Значит, главное вложение — проверки (гейты), а не новые агенты.
2. **Хрупкие файлы совпадают с ядром IPC.** Больше всего исправлений за полгода в таких файлах:

   | Файл | Коммитов-исправлений |
   |---|---|
   | `nxt_h1proto.c` | 14 |
   | `nxt_unit.c` | 11 |
   | `nxt_router.c` | 8 |
   | `nxt_conf_validation.c` | 8 |
   | `nxt_port_socket.c` | 7 |
   | `nxt_port_memory.c` | 6 |

   К ним относятся открытые задачи #425 (UAF в release-сборке), #414, #407, #394 (неограниченная очередь `port->messages`), #343, #341 (сообщения порта без аутентификации), #172 (защита shmem от враждебного приложения).
3. **Гипотезы плана совпадают с открытыми задачами.** Лимит фрагментов относится к #394. Правило snapshot-then-validate для SHM и `nxt_app_queue_cancel` — к #172. Это одни и те же дефекты, их не нужно дублировать новыми задачами.
4. **CI уже готов стать гейтами.** Из последних 100 прогонов 99 зелёные. ASan/UBSan, Lint, Clang AST, Syscall Drift и Fuzzing стабильны. Единственный красный — сборка на rolling-дистрибутивах (#384), и это окружение, не код.
5. **Кластер для демо фабрики.** В задачах #422, #429, #430, #434 и #435 одна и та же ошибка: `max_frame_size` для WebSocket игнорируется в языковых модулях. Один шаблон повторяется в N модулях — лучшая задача на D1.
6. **Cron / `schedules`.** Задач в трекере про это нет. Это новая функция FreeUnit для DrupalCon, её проект описан в разделе 5.

## 2. Конвейер фабрики

```
fidx: уровень + срез контекста (без LLM)
 -> ast-grep fix (L1, без LLM)
 -> исполнитель: Haiku (L1) / Sonnet (L2, L3) / Fable или Opus (L4) -> JSON-правка {fid, base_body_sha, replace_function}
 -> применение + проверка границ правки + переиндексация (без LLM)
 -> G1 сборка -Werror --hardening=strict
    G2 ./build/tests + срез pytest; правка src без теста не проходит
    G3 ASan/UBSan (TSan для L4)
    G4 фаззер 5 минут
    G5 ast-grep scan --error; дизассемблер горячих функций
    G6 @contract для IPC-функций
 -> не больше 2 итераций, затем эскалация на уровень выше
 -> ревью Fable (для IPC принимает Opus); рецензент не видит рассуждений исполнителя
 -> принять или отклонить, запись в experiment.jsonl
```

Как выбирать, что делать первым: **горячесть по профилю × риск по признакам из индекса × частота изменений в git**.

Размер PR: 70–150 строк, одно исправление на PR, обновления версий зависимостей отдельными PR. Темп: 5–8 PR в день, потому что ревьюер один.

## 3. Бюджет Max 5x

Расход: примерно 0.5–1.5 млн токенов в день. На D3 и D5 больше, на DC меньше 0.5 млн.

Если лимит кончается, урезаем в таком порядке:
1. Повторные прогоны при замере моделей.
2. Перекрёстное сравнение моделей на L3.
3. Двойное ревью IPC.
4. L4 целиком.
5. Opus-оркестратор (заменяем скриптом и Sonnet).

Гейты, `schedules` и фаззер не урезаем.

## 5. `schedules`: аналог cron для Drupal 12

```json
"schedules": {
  "drupal-cron": {
    "pass": "applications/drupal/index",
    "uri": "/cron/SECRET_KEY",
    "interval": 300, "jitter": 15, "timeout": 240,
    "overlap": "skip", "headers": {"Host": "example.org"}
  }
}
```

**Проверка конфига:** в `nxt_conf_validation.c`, по образцу `nxt_conf_vldt_app_limits_members` (стр. 1370).

**Разбор в router:** `nxt_router_conf_create` (`src/nxt_router.c:2528`).

**Запуск:**
- таймер ставится на `app->engine`, по образцу `idle_timer` (`src/nxt_router.c:2838`);
- запрос создаёт `nxt_http_request_create` (`src/nxt_http_request.c:249`) с `r->proto.any = NULL`;
- запрос идёт в приложение через `nxt_http_application_handler`.

**Главный риск:** `r->conf->socket_conf` используется без проверки. Нужен внутренний joint со счётчиком ссылок.

**План B:** loopback-клиент через `nxt_h1p_peer_connect`, либо внешний таймер и `curl --unix-socket`.

**Для Drupal без `schedules`:** `automated_cron` уже работает, потому что есть `fastcgi_finish_request()` (`src/nxt_php_sapi.c:228`).

## 6. FreeUnit Drupal Harness

**Что поднимается одной командой `docker compose up`:**
- FreeUnit с PHP 8.5;
- Drupal CMS и база данных;
- `schedules`;
- OTel collector, Prometheus, Tempo и Grafana. Это тот же стек, что поднимает DDEV-аддон **Gander** — фреймворк замеров производительности, встроенный в ядро Drupal с версии 10.2.

**Главная идея:** спаны Drupal (Gander: SQL, кеш, рендер) и спаны FreeUnit (router → IPC → worker, `src/nxt_otel.c`) попадают в **один трейс**.

Дашборд строится как дерево сворачиваемых полей: запрос → FreeUnit (router / IPC / worker) → Drupal (SQL / кеш / рендер) → функция (`fid`: контракт, гейты, доля в профиле, история изменений в git). Отдельные ветки: `schedules`, фабрика кода, процессы и нагрузка.

**Слои анализа и когда они работают:**

| Когда | Слои |
|---|---|
| На каждый PR (без нагрузки) | раскладка структур (`pahole`), граф управления и циклы, автоматы состояний, машинный код и `llvm-mca` |
| Под нагрузкой | `perf stat` / `perf c2c`, флейм-графы по процессам, OTel + USDT / bpftrace, `/status` |

## 8. Чего не делать

- Не обновлять «каждую функцию» за 8 дней.
- Не менять порядки атомиков и раскладку SHM до DrupalCon.
- Не включать `-Wconversion` глобально.
- Не принимать правки LLM, которые не прошли G1–G6.
- Не вызывать `sg`: это shadow-utils, нужен бинарь `ast-grep`.
- Не строить правки на препроцессированном коде.
- Не гнаться за детерминизмом на уровне инструкций между разными компиляторами.
