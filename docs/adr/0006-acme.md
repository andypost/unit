# 0006. ACME (RFC 8555) certificates: external client first, small core fixes

- Status: proposed
- Date: 2026-09-24
- Stream: ACME research (design only; no `src/` change on this branch)
- Code base: every `file:line` below refers to commit `24364da4`. Re-check
  each line before editing. `nxt_controller.c` and `nxt_router.c` change
  often.
- Local validation: `unitd` built from `24364da4` with
  `./configure --openssl && make -j2 unitd`. It was driven under
  `unshare -n` on high ports, together with pebble 2.10.1 (a test ACME CA)
  and lego 4.35.2 (see Appendix B). Let's Encrypt staging could not be
  reached from the sandbox: the egress proxy refused the CONNECT with 403.

## Context and problem statement

Operators want FreeUnit to get and renew TLS certificates by itself, the
way Caddy, FrankenPHP (which is Caddy), Traefik and nginx do. nginx does it
with the `ngx_http_acme_module` / `nginx-acme` module (2025, Rust). Upstream
NGINX Unit never shipped this. The request dates from 2020 in
nginx/unit#424 ("Integrated certbot in unit"). nginx/unit#547 ("Best
practice about certificate rotation") shows that users rotated certificates
by hand with `curl`. Upstream documented only a certbot how-to:
unit.nginx.org/howto/certbot. That site is blocked from this sandbox, so
the how-to is known only from search snippets: build a bundle, upload it
under a new name, and repoint the listener. nginx/unit is archived
read-only (Oct 2025).

This ADR asks two questions. What in FreeUnit stands in the way? What is
the smallest sound design? The owner wants little code: the smallest core
change that makes an external client, or a unitctl client, robust.

## Decision drivers

- **Little C.** Every line in the privileged main process, or in the
  router, is a line to audit.
- **No new privilege paths.** Main runs as root. Router and controller drop
  to `--user` (`src/nxt_process.c:1074-1170`, `nxt_process_core_setup` →
  `nxt_process_apply_creds` → `nxt_credential_setuid`). Application code
  must not gain control-plane access.
- **Zero-downtime rotation.** In-flight and keep-alive connections must
  survive. New handshakes must get the new certificate.
- **Atomic, persistent state.** A crash in the middle of a rotation must
  never leave a torn bundle in the statedir.
- **Reuse proven ACME clients.** certbot, lego and acme.sh already handle
  ARI, rate limits, EAB, DNS-01 providers and CA quirks.

## The code today

### 1. The certificate store

- **Location.** The certificates live in `<statedir>/certs/`
  (`src/nxt_runtime.c:973-982`). There is one file per bundle, and it is
  named exactly after the API name. The file holds the raw uploaded PEM
  (chain plus key), owned by root with mode 0600
  (`NXT_FILE_OWNER_ACCESS`, `src/nxt_file.h:184`).
- **Startup.** `nxt_cert_store_load()` (`src/nxt_cert.c:922-1036`) runs in
  main before the controller forks (`src/nxt_controller.c:223`). It opens
  **every** directory entry except `.` and `..` (`:966-968`), and hands the
  fds to the controller. The controller parses them into the in-memory
  metadata hash `nxt_cert_info` (`nxt_cert_info_init`, `:408-425`). That
  hash is what `GET /certificates` returns and what config validation
  consults (`nxt_conf_vldt_certificate_element`,
  `src/nxt_conf_validation.c:3357-3390`).
- **`PUT /certificates/<name>`** is handled by
  `nxt_controller_process_cert()` (`src/nxt_controller.c:1866-2040`):
  1. If the name already exists, it is refused with 400 **"Certificate
     already exists."** (`:1929-1933`, `:1997-2004`).
  2. The body is parsed by `nxt_cert_mem()` → `nxt_cert_bio()`
     (`src/nxt_cert.c:79-335`). This checks the PEM structure only: it
     needs one key and at least one certificate. **It does not check that
     the key matches the leaf** (`:318-331`).
  3. The metadata is saved **before** the file is written (`:1940`).
  4. The controller sends `CERT_GET` to main (`:1948`). Main
     (`nxt_cert_store_get_handler`, `src/nxt_cert.c:1235-1320`) opens
     `certs/<name>` with `O_RDWR|O_CREAT`. There is no `O_TRUNC`, no
     temporary file and no rename (`:1295`). Main passes the fd back.
  5. The controller `write()`s the body into that fd, and does **not check
     the result** (`src/nxt_controller.c:2069`).
- **`DELETE /certificates/<name>`** is refused with **"Certificate is used
  in the configuration."** when `nxt_controller_cert_in_use()`
  (`:2084-2135`) finds the name in any `listeners/*/tls/certificate`,
  either a string or an array element (`:1953-1957`). Otherwise the
  controller sends `CERT_DELETE`, which main accepts only from the
  controller's kernel-validated pid (`src/nxt_cert.c:1348-1390`).
- **Postponement.** Neither PUT nor DELETE on `/certificates` calls
  `nxt_controller_check_postpone_request()`. The config paths do call it
  (`src/nxt_controller.c:1455`, `:1585`). So a certificate operation can
  interleave with a reconfiguration that is still in flight.

### 2. How the router loads certificates (per listener, per reconfiguration)

- **Parsing the listener.** For each listener with `tls.certificate`, the
  router builds `nxt_tls_init_t`: cache_size, timeout, `conf_commands`
  and tickets (`src/nxt_router.c:3094-3130`). It also queues one
  `nxt_router_tlssock_t` per bundle name (`nxt_router_conf_tls_insert`,
  `:3274-3292`).
- **Loading each bundle.** For every queued name the router asks main for
  an fd: `nxt_cert_store_get()` → `CERT_GET` (`:2067-2075`). Main allows
  this from either the controller or the router
  (`src/nxt_cert.c:1262-1263`). The same `O_RDWR|O_CREAT` open applies, so
  **the unprivileged router receives a writable fd to private-key
  material**. A router request for a missing name would also create an
  empty file.
- **Building the context.** `nxt_router_tls_rpc_handler()`
  (`src/nxt_router.c:4051-4115`) calls `server_init` =
  `nxt_openssl_server_init()` (`src/nxt_openssl.c:216-370`). That
  function makes a **fresh `SSL_CTX` on every reconfiguration** from the
  fd (`nxt_openssl_chain_file`, `:373-470`: the leaf first, then the
  chain, then the key, then `SSL_CTX_check_private_key`, `:440-446`). It
  then applies `conf_commands` (`:296-301`) and sets the SNI callback when
  the listener has more than one bundle (`:350-354`;
  `nxt_openssl_servername`, `:1027-1108`, `SSL_set_SSL_CTX` at `:1096`).
- **Lifetime.** The old `nxt_socket_conf_t` and its `SSL_CTX` are freed
  only when their last joint reference is dropped
  (`src/nxt_router.c:5311-5350`, `server_free` at `:5348-5349`). So an
  established connection keeps the context it was accepted with.

**Consequence (verified, Appendix B.2):** *any* successful
reconfiguration reloads *every* certificate from disk. Two things follow:

1. The workaround used by certbot users today already rotates with zero
   downtime: upload under a new name, repoint the listener, delete the old
   name.
2. An in-place update only needs an atomic file replacement and a
   reconfiguration. No new router mechanism is needed.

### 3. TLS configuration surface

`tls` accepts only `certificate` (a string or an array of names),
`conf_commands` and `session` (`src/nxt_conf_validation.c:640-661`). SNI is
implicit: the bundle names are matched against the SAN and CN of each
certificate (`nxt_openssl_cert_get_names`, `src/nxt_openssl.c:805-918`).

**There is no ALPN anywhere in `src/`.** `grep -ri alpn src/` returns
nothing, and ADR 0005 confirms this (`docs/adr/0005-http2-http3.md:119`).
TLS-ALPN-01 needs an ALPN select callback that accepts `acme-tls/1`. It
also needs a per-SNI ephemeral certificate carrying the `acmeIdentifier`
extension (RFC 8737). Verified: `openssl s_client -alpn acme-tls/1` against
a FreeUnit listener prints "No ALPN negotiated".

### 4. Serving HTTP-01 today

Routes with `share` can serve `/.well-known/acme-challenge/<token>` from a
directory on a plain-HTTP listener, before any TLS listener exists. The
relevant members are `share`, `chroot`, `fallback` and `follow_symlinks`
(`src/nxt_conf_validation.c:896-930`). Verified with pebble plus lego
(Appendix B.3):

- A token is served with 200 and the exact key authorization.
- A missing token gets 404, from `fallback`.
- `../` traversal is refused with 400 by the URI normaliser.
- All other paths are redirected with 301 to `https://$host$request_uri`.
  Let's Encrypt follows redirects to 443 and ignores the certificate there,
  so the redirect is harmless.

There are two operational gotchas:

1. The listener must `"pass": "routes/…"`, not straight to an application.
2. **The router reads the token as the unprivileged `--user`.** The
   webroot and every directory above it must be traversable by that user.
   In the first local run, every validation failed with
   `opening "<token>" ... failed (13: Permission denied)` because a parent
   directory was mode 0700.

The `return` action takes a status and a `location` only
(`src/nxt_conf_validation.c:882-892`). It cannot carry a body, so a
"challenge via config, no filesystem" trick is not possible today.

### 5. Schedules (ADR 0004)

A schedule can only `pass` to an **application**: `nxt_http_action_create`,
then "is not an application" (`src/nxt_router_schedule.c:437-449`). The
longest interval is 2147483 s, about 24.8 days
(`src/nxt_router_schedule.h:29`). Daily renewal checks fit.

The problem is what the application would have to do. An ACME client
running as a FreeUnit application must reach the **control socket** to
upload a certificate. That hands control-plane power, which is root
equivalent, to an application worker. Applications are exactly the code
FreeUnit isolates. Schedules are therefore the wrong trigger for anything
that writes certificates. A systemd timer or cron, running as root or as a
dedicated user with socket access, is the right one.

### 6. Processes, privileges, outbound network

| Process | Runs as | Relevant capability |
|---|---|---|
| main | root | owns `<statedir>/certs` (0600), `nxt_main_file_store()` atomic writer (`src/nxt_main_process.c:1990-2105`) |
| controller | `--user` | parses PEM (links OpenSSL through `nxt_cert.c`), owns the metadata, serves the control API |
| router | `--user` | builds `SSL_CTX`s, serves `share`, HTTP proxy **without TLS** (`src/nxt_http_proxy.c` has no TLS client) |
| apps | per app | isolated; no control access |

No FreeUnit process makes outbound HTTPS today. An embedded ACME client
would add three new things: a TLS client, a DNS resolution path (ACME
directory and nonce requests from inside the event loop), and account-key
storage. Doing that in root main breaks the "main does no network" rule.
Doing it in the router puts the CA account key in the process that parses
hostile traffic.

### 7. Existing tooling

- **`tools/unitctl`** is Rust 2021, with tokio, hyper 1, hyper-rustls and
  rustls behind the `tls` feature
  (`tools/unitctl/unit-client-rs/Cargo.toml:10-24`). It already uploads
  PEM bundles to `/certificates/<stem>.pem` and validates them client-side
  (`tools/unitctl/unitctl/src/cmd/import.rs:39-43`,
  `requests.rs:115-165`). It ships as deb, rpm, brew and a container.
  Adding `instant-acme`, which is itself built on hyper and rustls, fits
  the dependency tree it already has.
- **`tools/setup-unit`** is a 1.7k-line POSIX sh installer and REPL helper
  with no certificate logic. It could install the hook and timer from
  Appendix A, but it should not host an ACME client.
- **OTel** shows that a Rust static library can be linked into the core
  (`auto/otel`, `src/otel/`). This is the only precedent for option (c) in
  Rust.

### 8. What other servers do

- **Caddy and FrankenPHP** (CertMagic): the ACME client is in-process and
  the storage is pluggable, with locks for clusters. HTTP-01 and
  TLS-ALPN-01 are enabled by default. On-demand TLS is supported.
- **Traefik:** the ACME client is in-process. State is kept in one
  `acme.json` file, which cannot be shared between instances.
- **nginx `ngx_http_acme_module`** (Rust, 2025): configured with
  `acme_issuer`, `acme_certificate` and `acme_shared_zone`. Keys and certs
  are kept in `state_path` and in shared memory. It supports HTTP-01 and
  TLS-ALPN-01, not DNS-01. Certificates reach `ssl_certificate` through
  variables (`$acme_certificate`), so renewal needs no reload. It needs a
  `resolver`. (Sources: the nginx-acme GitHub README and search snippets.
  nginx.org itself is blocked from this sandbox.)

All four are single-binary servers whose worker model already includes an
outbound HTTPS client. FreeUnit's model does not.

## 1. Blockers

Classes: **hard** (a core change is needed), **soft** (config, tooling or
documentation) and **policy** (a security or ownership decision).

| # | Blocker | Evidence | Class |
|---|---|---|---|
| B1 | No in-place replacement. `PUT` on an existing name returns 400, and `DELETE` of an in-use name returns 400. Rotation must use a new name, repoint every listener, then delete the old name. | `src/nxt_controller.c:1929-1933`, `:1953-1957`, `:2084-2135` | soft today (the workaround works, Appendix B.2). It becomes hard for "the same name forever" semantics, which unitctl and humans expect. |
| B2 | The store write is not atomic. It uses `O_RDWR\|O_CREAT` with no `O_TRUNC`, temporary file or fsync, and the `write()` result is ignored. Reusing a name after DELETE is safe only because the file is unlinked first. | B3 | Metadata is saved before the file is stored. A failed store leaves a phantom certificate that validation accepts (`src/nxt_conf_validation.c:3382`). | `src/nxt_controller.c:1940-1949`, `:2045-2062` | hard (small) |
| B4 | A key/leaf mismatch is accepted at upload and fails later, at listener apply. `test_tls_certificate_key_incorrect` pins this behaviour. | `src/nxt_cert.c:318-331`, `src/nxt_openssl.c:440-446`, `test/test_tls.py:188-210` | soft for external clients (the hook can verify). ## 2. Considered options

### (a) External client (certbot, lego, acme.sh) plus the control API

The client runs under a systemd timer or cron. It answers HTTP-01 through
a webroot served by a FreeUnit `share` route, or uses DNS-01 with no
FreeUnit involvement at all. A deploy hook uploads the bundle and swaps it
in. Appendix A has a working hook.

- **Security surface.** It is unchanged. The hook needs the control socket,
  exactly as an admin with `curl` does. Account keys stay in the client's
  own store (`/etc/letsencrypt`, the lego `--path`).
- **Core changes.** None are needed to work (verified). The recommended
  hardening is B2, B3, B4, B5 and B6, plus in-place PUT (B1). These make
  the hook a one-liner and remove its read-modify-write of
  `/config/listeners`.
- **Effort.** Phase 0 (hook plus documentation) takes about a day.
  Phase 1 (core) is roughly 200–300 lines of C plus tests, 2–3 days.
- **Packaging.** Ship `freeunit-deploy-hook` in the packages (for example
  `/usr/share/unit/acme/`) and a certbot `renewal-hooks/deploy` symlink
  recipe. The distro certbot or lego does the rest.
- **Coverage.** All challenge types the client supports, including DNS-01
  and wildcards. ARI, EAB and non-Let's Encrypt CAs come free.

### (b) An ACME client in `unitctl` (Rust) driving the control API

This would be `unitctl acme issue|renew --domain … --webroot …`, using the
`instant-acme` crate. There are two ways to handle HTTP-01. With a webroot,
it is the same `share` route as in (a). Or unitctl could insert a temporary
route itself, but `return` cannot carry a body (§4), so a transient route
would still need a file, or a new core feature. Renewal would run from a
systemd timer. Not from schedules (B10).

- **Security surface.** It is the same as (a), plus a new ACME
  implementation to maintain, plus an account key that unitctl must store
  (0600, root or a dedicated user).
- **Core changes.** The same as the Phase 1 hardening in (a). Without
  in-place PUT, unitctl would reimplement the generation-rename dance.
- **Effort.** About 800–1500 lines of Rust: account management, orders,
  challenge files, CSR and key generation (rcgen), a renewal policy
  (ARI or 1/3 of the lifetime), rate-limit backoff, state, man page and
  tests. That is one to two weeks, and a long tail of CA quirks that
  certbot and lego have already absorbed.
- **Packaging.** It is already a deb/rpm/brew artifact. The musl
  `--no-default-features` build currently drops TLS
  (`tools/unitctl/unitctl/Cargo.toml:13-16`), so ACME would force TLS back
  into that build.
- **Coverage.** HTTP-01 and optionally DNS-01 through a hook. It
  duplicates lego for a nicer UX.

### (c) Embedded client in main or the controller (C, or Rust like OTel)

Configuration would live in `"tls": {"acme": {...}}`. HTTP-01 would be
answered by an internal router route. TLS-ALPN-01 would be optional.

- **Security surface.** This is the largest option. It needs outbound
  HTTPS and DNS from inside FreeUnit (B8). Main is root and must not do
  network I/O. The controller is unprivileged, but it is the process that
  accepts control-API input. The router parses the internet. A fourth
  process type is the only clean home: forked by main, `--user`, network
  only, no listeners. The account key and in-progress orders become new
  statedir secrets (B9). Challenge tokens would have to flow controller →
  router over the port protocol.
- **Core changes.**
  - a new process type, or a Rust static library in the controller;
  - an async HTTPS client (none exists; the proxy action is HTTP only);
  - resolver integration;
  - a timer-driven renewal state machine that survives restarts;
  - an internal challenge route in the router: a new action or a reserved
    route checked before `routes`;
  - atomic in-place rotation (B1–B3);
  - for TLS-ALPN-01: ALPN (B7) plus per-SNI ephemeral certificates;
  - new config validation, `/status` fields and documentation.
- **Effort.** Several thousand lines, and weeks to months including the
  tests (pebble in CI) and the security review.
- **Packaging.** A Rust build dependency in the core, like `--otel`, or a
  large C ACME implementation. Either way it must be kept current with CA
  changes: ARI, profiles, short-lived certificates.
- **Coverage.** HTTP-01 and TLS-ALPN-01 only, as in nginx-acme. DNS-01
  would need provider plugins, which no embedded client does well.

### Comparison

| | (a) external plus hook | (b) unitctl | (c) embedded |
|---|---|---|---|
| New privileged or network code in unitd | none | none | high (B8, B9) |
| Core C changes | Phase 1 hardening (~250 lines) | the same | the same, plus client, route, ALPN, process |
| New code to maintain | ~60-line hook | ~1k lines of Rust | several thousand lines |
| Challenge types | all (HTTP-01, DNS-01, wildcard) | HTTP-01 (DNS-01 via hook) | HTTP-01 (+ TLS-ALPN-01) |
| Zero-downtime rotation | yes (verified) | yes | yes |
| "Just works" UX | good with a packaged hook | better | best |
| Time to ship | days | weeks | months |

## 3. Decision outcome

**Chosen: option (a), with a small Phase 1 core change that makes
in-place certificate replacement atomic and safe.** Option (b) is left
open as a later UX layer on top of the same core change. Option (c) is
rejected for now. Nothing in the core should do outbound ACME until there
is a separate unprivileged network process with a clear owner, and ALPN
exists (ADR 0005).

No new HTTP-01 helper is added to the core. `share` already serves
challenges correctly (verified with pebble). A config-only challenge
action would duplicate `share` and add a way to inject response bodies
through the control API.

### Phase 0: documentation and hook (no core change)

1. Add `freeunit-deploy-hook` (Appendix A.3) to the packages, for example
   `pkg/…/usr/share/unit/acme/freeunit-deploy-hook`, together with the
   HTTP-01 route snippet (A.2), the certbot and lego recipes (A.4, A.5),
   and a systemd timer example.
2. Document B11 and B12: the listener must pass to routes, the webroot
   must be readable by the `--user`, and the statedir must never be edited.
3. Optionally, add a `setup-unit acme` helper that only installs the hook
   and the timer.

### Phase 1: atomic in-place replacement (core, about 250 lines)

Target semantics: `PUT /certificates/<name>` on an **existing** name
replaces the bundle atomically. If a listener uses the name, the controller
re-applies the current configuration, so new handshakes get the new
certificate while existing connections keep theirs. The response is sent
after the router acknowledges. Changes by file:

1. **`src/nxt_cert.c`: validate harder (B4).** In `nxt_cert_bio()`, after
   the loop (around `:318`), add a check before `return cert`:

   ```c
   if (X509_check_private_key(cert->chain[0], cert->key) != 1) {
       nxt_openssl_log_error(task, NXT_LOG_ALERT,
                             "certificate and private key do not match");
       goto fail;
   }
   ```

   The upload is then rejected with 400 "Invalid certificate." instead of
   failing later at listener apply. Update `test_tls_certificate_key_incorrect`
   (`test/test_tls.py:188-210`) to expect `error` on upload.
2. **`src/nxt_cert.c`: a reserved namespace for temporaries (B13).** In
   `nxt_cert_store_load()` (`:966`), skip every name starting with `.`.
   In `nxt_controller_process_cert()`, reject names starting with `.` with
   400 "Invalid certificate name."
3. **`src/nxt_main_process.c`, `src/nxt_port.h`, `src/nxt_cert.c`: an
   atomic store message (B2, B6).**
   - Add `_NXT_PORT_MSG_CERT_STORE` / `NXT_PORT_MSG_CERT_STORE`, the
     `cert_store` handler slot, and wire it in the main handler table next
     to `cert_get` and `cert_delete` (`src/nxt_main_process.c:846-847`).
   - Add a main handler, `nxt_cert_store_put_handler()`. It accepts the
     message only from the controller's kernel-validated pid (the same
     guard as `nxt_cert_store_delete_handler`, `src/nxt_cert.c:1357-1370`).
     The payload is the NUL-terminated name plus a `size_t` in the buffer,
     and the bundle arrives in an shm fd, exactly as
     `nxt_controller_conf_store()` sends `conf.json`
     (`src/nxt_controller.c:2619-2665`, `src/nxt_main_process.c:1875-1966`).
     The handler calls
     `nxt_main_file_store(task, rt->certs.start, "<certs>/.<name>.tmp", "<certs>/<name>", p, size)`.
     That helper already writes an `O_EXCL` temporary, loops over short
     writes, fsyncs, renames and fsyncs the directory
     (`src/nxt_main_process.c:1990-2105`). Export it as `nxt_main_file_store()`,
     or make `nxt_main_test_run_file_store()` (`:754-758`) the real public
     name. Reply with `RPC_READY_LAST` or `RPC_ERROR`.
   - Add a controller-side sender, `nxt_cert_store_put(task, name, mbuf, mp, handler, ctx)`.
   - Make `nxt_cert_store_get_handler()` read-only: `NXT_FILE_RDONLY`
     and `NXT_FILE_OPEN`, no create (`src/nxt_cert.c:1295`). Only
     `CERT_STORE` writes from now on. This closes B6.
4. **`src/nxt_controller.c`: PUT becomes create-or-replace (B1, B3, B5).**
   - At the top of the PUT/DELETE branch of `nxt_controller_process_cert()`
     (after `:1927`), call `nxt_controller_check_postpone_request()` and
     queue the request, as `/config` does (`:1455`).
   - Remove the `exists_cert` refusal (`:1929-1933`).
   - Parse with `nxt_cert_mem()`. On success, call `nxt_cert_store_put()`.
     Do **not** call `nxt_cert_info_save()` yet.
   - In the store callback, which replaces
     `nxt_controller_process_cert_save`, `:2045-2078`:
     - on error, return 500 and leave the metadata untouched (B3);
     - on success, call `nxt_cert_info_save()` (already `replace = 1`,

     - if the certificate is new, or `nxt_controller_cert_in_use()` is

     - otherwise call `nxt_controller_conf_send(task, mp, nxt_controller_conf.root, nxt_controller_cert_apply_handler, req)`,
       using a cloned pool as `nxt_controller_send_current_conf()` does
       (`:458-470`).

     updated." when the router acknowledges.
   - If the router rejects the configuration, which is possible only
     through things upload validation cannot see (for example a

### Phase 2 (optional, later): `unitctl acme`

Build this only if users ask for a batteries-included UX. It would be an
`instant-acme`-based subcommand that writes HTTP-01 tokens into the
documented webroot and PUTs the bundle in place (Phase 1). It would ship a
systemd timer unit, and it would not use schedules (B10).

### Phase 3 (deferred): TLS-ALPN-01

Revisit once ADR 0005 adds `SSL_CTX_set_alpn_select_cb()`
(`docs/adr/0005-http2-http3.md:284-295`). TLS-ALPN-01 would additionally
need three things: the callback must accept `acme-tls/1`; the servername
callback must select an ephemeral challenge `SSL_CTX` by SNI; and the
handshake must be closed right after it completes. That is only worth
doing together with option (c).

### Consequences

- **Good.** Almost no new attack surface. Every ACME feature (DNS-01,
  wildcards, ARI, EAB, other CAs) is available on day one. Rotation is
  atomic and crash-safe. Clients no longer need to rename bundles.
- **Bad.** No "one JSON key" auto-HTTPS like Caddy. Operators install
  certbot or lego and a timer. The Phase 0 hook depends on `jq` and `curl`.
- **Neutral.** The in-place update PUT also re-applies the full
  configuration, which touches every listener's `SSL_CTX`. That cost is
  already paid by any config change today.

## Pros and cons summary

- (a) is simple, safe, complete and quick to ship, at the cost of
  onboarding UX.
- (b) gives better UX, at the cost of a Rust ACME client to maintain, an
  account key in a second tool, and TLS back in the musl build.
- (c) gives the best UX, at the cost of network-capable privileged code,
  ALPN, a new process type, and months of work.

## Appendix A: working manual recipe (today's FreeUnit, no core change)

### A.1 Bootstrap order

1. Configure only port 80 with the challenge route (A.2).
2. Run the ACME client once with `--webroot`. The hook uploads the first
   bundle.
3. Add the 443 listener with `"tls": {"certificate": "<name>"}`.
4. Renewals then go through the timer and the hook. There is no restart.

### A.2 HTTP-01 route (port 80)

```json
{
  "listeners": {
    "*:80":  { "pass": "routes/http" },
    "*:443": { "pass": "routes/app", "tls": { "certificate": "example.org" } }
  },
  "routes": {
    "http": [
      {
        "match": { "uri": "/.well-known/acme-challenge/*" },
        "action": {
          "share": "/var/lib/unit-acme$uri",
          "chroot": "/var/lib/unit-acme/.well-known/acme-challenge/",
          "fallback": { "return": 404 }
        }
      },
      { "action": { "return": 301, "location": "https://$host$request_uri" } }
    ],
    "app": [ { "action": { "pass": "applications/app" } } ]
  }
}
```

`/var/lib/unit-acme` and every directory above it must be traversable
(`o+x`, or group-accessible) by FreeUnit's `--user`, because the router
opens the token as that user. The token files must be readable by it too.
certbot and lego write them 0644, subject to umask. Leave out the `*:443`
listener until the first bundle exists: validation rejects a listener that
names a missing certificate.

### A.3 `freeunit-deploy-hook`

This hook works on current FreeUnit. It is idempotent and handles string
and array `certificate` values.

```sh
#!/bin/sh
# certbot deploy hook (also usable from lego --deploy-hook / acme.sh --reloadcmd):
# upload the renewed bundle to FreeUnit under a fresh name, repoint every
# listener that used an older generation of it in ONE reconfiguration, then
# delete the generations nothing references any more.
#
#   certbot: RENEWED_LINEAGE=/etc/letsencrypt/live/example.org
#   others : CERT_FULLCHAIN=... CERT_KEY=... UNIT_CERT_BASE=example.org
set -eu

SOCK=${UNIT_CONTROL:-/var/run/unit/control.sock}
FULLCHAIN=${CERT_FULLCHAIN:-${RENEWED_LINEAGE:-}/fullchain.pem}
KEY=${CERT_KEY:-${RENEWED_LINEAGE:-}/privkey.pem}
BASE=${UNIT_CERT_BASE:-$(basename "${RENEWED_LINEAGE:?set RENEWED_LINEAGE or UNIT_CERT_BASE}")}
NEW="$BASE@$(date -u +%Y%m%dT%H%M%SZ)"

api() { curl -fsS --unix-socket "$SOCK" "$@"; }

# 1. Upload.  A new name every time: PUT on an existing name is refused.
cat "$FULLCHAIN" "$KEY" \
    | api -X PUT --data-binary @- "http://localhost/certificates/$NEW" >/dev/null

# 2. Repoint: "BASE" or "BASE@<stamp>" -> NEW, strings and arrays alike.
#    One PUT of /config/listeners is one atomic reconfiguration.
api http://localhost/config/listeners \
    | jq --arg base "$BASE" --arg new "$NEW" '
        def gen: type == "string" and (. == $base or startswith($base + "@"));
        map_values(
          if (.tls.certificate? // null) == null then .
          elif (.tls.certificate | type) == "array"
            then .tls.certificate |= map(if gen then $new else . end)
          else .tls.certificate |= (if gen then $new else . end)
          end)' \
    | api -X PUT --data-binary @- http://localhost/config/listeners >/dev/null

# 3. Garbage-collect older generations.  A generation still in use (e.g. by
#    a listener this hook does not know about) is refused and kept.
api http://localhost/certificates \
    | jq -r --arg base "$BASE" --arg new "$NEW" '
        keys[] | select((. == $base or startswith($base + "@")) and . != $new)' \
    | while read -r old; do
        api -X DELETE "http://localhost/certificates/$old" >/dev/null 2>&1 \
            || echo "freeunit-deploy-hook: kept $old (still in use)" >&2
      done

echo "freeunit-deploy-hook: $BASE -> $NEW"
```

Caveats:

- Step 2 is a read-modify-write of `/config/listeners`. It can race with a
  concurrent admin edit. Phase 1 removes the need for it.
- If the upload fails with "Invalid certificate.", nothing changes.
- If the key does not match the certificate (B4), the upload succeeds but
  step 2 fails with "Invalid configuration."; `set -e` stops the hook
  before the old generation is deleted, so the old bundle is still served.

### B.2 Rotation under a live TLS listener (self-signed a → b)

`probe.py` did the following, in order:

1. Opened a keep-alive TLS connection and made a request.
2. Opened a second connection and sent only half of the request headers.
3. Rotated with `PUT /certificates/b` followed by
   `PUT /config/listeners/*:18443/tls/certificate "b"`.
4. Finished the half-sent request.
5. Reused the keep-alive connection.
6. Opened a new connection.
7. Deleted `a` and reused the old connection once more.

Fingerprints: a=`dcb4366317903236`, b=`b9ba0a1d375d6d43`.

```
== in-place replace of a bundle in use
{ "error": "Certificate already exists." }
== delete a bundle in use
{ "error": "Certificate is used in the configuration." }
== probe rotation (a -> b)
keepalive conn  cert: dcb4366317903236 resp: HTTP/1.1 200 OK
rotate         : { "success": "Certificate chain uploaded." } { "success": "Reconfiguration done." }
in-flight req   cert: dcb4366317903236 resp: HTTP/1.1 200 OK
keepalive after  cert: dcb4366317903236 resp: HTTP/1.1 200 OK
new conn        cert: b9ba0a1d375d6d43 resp: HTTP/1.1 200 OK
delete old      : { "success": "Certificate deleted." }
keepalive after delete cert: dcb4366317903236 resp: HTTP/1.1 200 OK
```

Findings:

- An in-place PUT and a DELETE of an in-use bundle are both refused (B1).
- The generation swap drops nothing. The in-flight request and the
  keep-alive connection complete on the old `SSL_CTX`, even after the old
  bundle is deleted from disk and from the API. New handshakes get the new
  certificate immediately after "Reconfiguration done."

**Experiment 2** (the basis for B12 and for "reconfiguration reloads
everything"):

1. Overwrite `<statedir>/certs/b` on disk with bundle `a`, behind the API.
2. Re-PUT the unchanged value `"b"` to the listener. The router accepts
   this no-op configuration.
3. New handshakes now serve `a` (`dcb4366317903236`).
4. `GET /certificates/b` still describes the old metadata.

So the router re-reads every bundle on every reconfiguration. The in-place
update in Phase 1 needs only an atomic file store plus a reconfiguration.

The **hook** (A.3) was run twice against listeners `*:18443`
(`"example.test"`) and `*:18444` (`["other", "example.test"]`):

