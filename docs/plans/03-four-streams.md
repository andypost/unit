# FreeUnit: 4 потока

Коды задач (A1, B2, C3…) взяты из `freeunit-streams.md`. Здесь задачи перегруппированы в четыре потока с понятными владельцами.

## 1. КОД: корректность и безопасность, фабрика кода

**Цель:** закрыть классы уязвимостей, довести фабрику до рабочего состояния, закрыть реальные баги.

**Содержимое:**
- инструменты фабрики: индекс функций, срезы контекста, применение правок, конвейер (A1–A7);
- гейты и hardening: `--hardening`, `nxt_checked.h` / `nxt_span.h`, ast-grep, гейт «правка без теста не проходит», ADR-0001, ASan-poisoning (B1–B7);
- баги:
  - WebSocket `max_frame_size` (#422/#429/#430/#434/#435);
  - #431;
  - IPC: `mmap_read`, `prepare_msg`, #172, #394, #425;
  - фаззер `nxt_unit_msg_fuzz` (C1–C8);
- замер моделей на 18 функциях (G1–G5).

**Не входит:** порядок атомиков, раскладка SHM, производительность.

**По дням:**

| День | Задачи |
|---|---|
| D1 | A1–A5, B1, B2, B6, C1, C2 |
| D2 | A6, A7, B3–B5, G1 |
| D3 | C3–C8, G2 |
| D4–D5 | G3–G5, стабилизация |
| DC | только механика, закрытие задач |

**Для других потоков:** хелперы B2 (для `schedules`), `--hardening` (для образа), индекс `fid` (для наблюдаемости и оптимизаций).

## 2. ОПТИМИЗАЦИИ: производительность C-ядра и PHP-стека

**Цель:** измеримые и безопасные улучшения. Всё рискованное оформляется как доказанный кандидат в бэклог.

**Содержимое:**
- **O1.** Микробенчмарк очередей и IPC в `src/test/`: `nxt_nncq`, `nxt_app_queue`, `nxt_port_queue`, круговой путь mmap-чанка.
- **O2.** Базовые замеры: `perf stat` (instructions, cycles, cache-misses, branch-misses) и флейм-графы для router, worker и приложения. Нагрузка: hello-world 1 КБ / 64 КБ и Drupal. Привязка к `fid` (F2).
- **O3.** `tools/disasm-diff.sh` для ~15 горячих функций и закреплённый образ clang.
- **O4.** `perf c2c` и `pahole`: подтвердить ложное разделение кеш-линий на `nitems`, head/tail `nncq` и `nxt_app_queue_item_t`. Только замер, изменения в бэклог (это смена ABI SHM).
- **O5.** Безопасные улучшения без смены ABI:
  - hot/cold-раскладка `struct nxt_port_s` (`src/nxt_port.h:316`): структура живёт внутри процесса и не лежит в SHM;
  - `__attribute__((cold))` на функциях обработки ошибок;
  - опциональные `--lto` и `--pgo-gen` / `--pgo-use`.
- **O6.** Настройка PHP и Drupal: OPcache и preload, `processes` dynamic/static, `limits.requests`, JIT on/off. Итог — таблица RPS и p99.
- **O7.** Litmus-модели (herd7 или GenMC) для `nncq` и `notified`. Это доказательная база для перехода на `__atomic` после DrupalCon.

**По дням:**

| День | Задачи |
|---|---|
| D2 | O1 |
| D3 | O2, O3 |
| D4 | O4, O5 |
| D5 | O6 (после образа Drupal) |
| DC1 | O6 под нагрузкой, O7 |

**Зависимости:** индекс из потока КОД (A3), образ из потока ДРУПАЛ (E3). Любая правка проходит гейты потока КОД.

**Критерий:** `instructions` на запрос не хуже базовой линии, у каждого изменения есть замер «до и после».

## 3. НАБЛЮДАЕМОСТЬ: трейсы, метрики, дашборд

**Цель:** один трейс от HTTP до SQL, и дашборд со сворачиваемыми полями.

**Содержимое:**
- **N1.** Прототип дашборда на демо-данных (артефакт). Утверждение структуры полей.
- **N2.** OTel FreeUnit (`src/nxt_otel.c`): проверить, что атрибуты спанов и контекст трассы доходят до PHP. Цель — чтобы спаны Drupal и Gander стали дочерними к спану FreeUnit, а не отдельным трейсом.
- **N3.** ~8 USDT-проб в IPC и `schedules` + скрипты `bpftrace` с гистограммами задержек (F3).
- **N4.** Расширение `/status`: глубина очередей, заполнение SHM, счётчики `schedules` (F4).
- **N5.** Экспорт: `/status` → Prometheus (экспортёр), OTel → collector → Tempo или файл.
- **N6.** Генератор дашборда: HTML-артефакт или Grafana JSON. Уровни дерева: запрос → FreeUnit → Drupal → функция (`fid`: контракт, гейты, профиль, история в git) → `schedules` → фабрика → процессы (F6).

**По дням:**

| День | Задачи |
|---|---|
| D1 | N1 |
| D3 | N2 |
| D4 | N3 |
| D5 | N5 |
| DC1 | N4 (после `schedules`) |
| DC2 | N6 |

**Зависимости:** флейм-графы из потока ОПТИМИЗАЦИИ (O2), профиль `observability` в образе (E6), `schedules` из потока ДРУПАЛ.

## 4. ДРУПАЛ И ОТЛАДКА: dev kit, `schedules`, инструменты отладки

**Цель:** один образ для код-спринтов и демо cron на FreeUnit.

**Содержимое:**
- **Образ** (E1–E4, E7):
  - `Dockerfile.drupal-core-dev-php8.5`;
  - конфиг FreeUnit для Drupal;
  - entrypoint с командами `si`, `test`, `lint`, `mr`;
  - SQLite, работа офлайн;
  - отдельный тег `:js`.
- **`schedules`** (D1–D8): поток владеет функцией целиком, включая C-код в `nxt_conf_validation.c` и `nxt_router.c`, и соблюдает порядок слияния с потоком КОД.
- **Отладка:**
  - **R1.** Xdebug в образе: `XDEBUG=1`, `xdebug.client_host`, готовый `launch.json` для VS Code и PhpStorm. Проверить совместимость Xdebug step-debug с процессной моделью FreeUnit: процессы приложения и таймауты. При отладке нужно поднимать `limits.timeout`, иначе router обрывает запрос на брейкпоинте.
  - **R2.** `unitd-debug` в образе (уже собирается): переключение `UNITD=unitd-debug`, debug-лог, `gdb` и `rr` в теге `:debug`. Документация: как подключиться к worker-процессу PHP.
  - **R3.** Команда `debug-request`: один запрос с полным трейсом, debug-логом FreeUnit и профилем Xdebug (или SPX / Excimer) для конкретного URL.
  - **R4.** Прогон `BrowserTestBase` из ядра под FreeUnit (E5). Расхождения передаются как задачи потоку КОД.

**По дням:**

| День | Задачи |
|---|---|
| D2 | формат `schedules`, E1, E2 |
| D3 | валидация и разбор `schedules`, E3, R1 |
| D4 | запрос и таймер `schedules`, E4, R2 |
| D5 | тесты `schedules`, E7, R3, R4, демо |
| DC3 | contribution day с образом |

**Зависимости:** хелперы B2 и `--hardening` из потока КОД, профиль наблюдаемости (N5).

**Критический путь демо:** B2 → проверка конфига `schedules` → разбор в router → внутренний запрос → таймер → интеграция в образ → демо.

## Как потоки связаны

```
КОД ── хелперы B2, гейты, индекс fid ──► ДРУПАЛ, ОПТИМИЗАЦИИ, НАБЛЮДАЕМОСТЬ
ДРУПАЛ ── образ, нагрузка Drupal ─────► ОПТИМИЗАЦИИ (O6), НАБЛЮДАЕМОСТЬ (N5)
ОПТИМИЗАЦИИ ── флейм-графы, baseline ─► НАБЛЮДАЕМОСТЬ (N6)
НАБЛЮДАЕМОСТЬ ── трейсы, дашборд ─────► ДРУПАЛ (демо), ОПТИМИЗАЦИИ (поиск узких мест)
```

**Общие файлы:**
- `nxt_conf_validation.c` и `nxt_router.c`: сначала КОД (#431, `prepare_msg`), потом ДРУПАЛ (`schedules`);
- `nxt_status.c`: только НАБЛЮДАЕМОСТЬ, после `schedules`;
- `auto/*`: владелец КОД, `--lto` и `--pgo` из потока ОПТИМИЗАЦИИ идут через него;
- `pkg/docker/*`: владелец ДРУПАЛ.

**Модели:**

| Поток | Основная модель | Кто подключается |
|---|---|---|
| КОД | Sonnet | Fable / Opus на IPC |
| ОПТИМИЗАЦИИ | Sonnet | Fable на анализ perf и litmus |
| НАБЛЮДАЕМОСТЬ | Sonnet | Haiku на конфиги |
| ДРУПАЛ | Sonnet | Opus на внутренний запрос `schedules` |

Одновременно не больше одного агента Opus или Fable.

**Решения человека** (#93, #386, #144, разбор задач) идут вне потоков, асинхронно.
